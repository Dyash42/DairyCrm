[ADM-02] <admin-persona|Customer management / scheduling|PRD-5.2|Admin> Deleting (soft-cancelling) a customer does NOT stop deliveries — milk keeps being scheduled
  @ apps/backend/src/modules/customers/index.ts:542-553
  WHAT: DELETE /customers/:id only flips Customer.status to CANCELLED. It does not cancel the customer's ACTIVE subscription. The daily route generator (jobs/daily-route-gen.ts listSubscriptionsActiveOn) queries `subscription.findMany({ where: { status: 'ACTIVE' } })` and the scheduling engine (services/scheduling.ts getDeliveriesForDate, lines 95-104) filters ONLY on `s.status !== 'ACTIVE'` — it never inspects customer.status.   IMPACT: An admin who 'removes' a customer (e.g. moved away, refused service, fraud) keeps getting them on the milkman's Today's Route and keeps accruing billable deliveries.   FIX: In the DELETE handler, wrap in a transaction that also sets all the customer's ACTIVE subscriptions to CANCELLED (and pending RenewalReminders/AutoResumeJobs to CANCELLED). Alternatively have the scheduling engine join customer.status and skip CANCELLED/non-ACTIVE customers.

[ADM-04] <admin-persona|Bulk import / backend|PRD-5.1|Admin> Bulk import commit trusts client rows verbatim — no re-validation, no DB phone re-check, no atomicity
  @ apps/backend/src/modules/customers/bulk.ts:33-35
  WHAT: POST /customers/bulk/commit accepts `rows: z.array(z.unknown())` and casts them to ValidatedRow without re-running validateCsv.   @ apps/backend/src/services/scheduling.ts:95-104

I have enough concrete evidence to produce the coverage-gap list. The findings already cover most major flows, so I'll focus on areas/files genuinely under-examined and not duplicating existing findings.

COVERAGE GAPS — areas/flows/files an auditor should still investigate (none duplicate the listed findings):

1. Migration completeness for the WHOLE schema, not just LocationToken (apps/backend/prisma/migrations/). DAT-01 flags lat/lng/LocationToken, but the audit never verified the rest of `0000_init` vs the live schema.prisma. Open question: are Product.imageUrl/sortOrder, Setting columns, QrCode.version, HolidayCalendar composite-unique, Delivery.confirmationSentAt/ratePerLitre, and the `updatedBy` columns ALL captured by the five committed migrations, or is there broader drift? `0002_holiday_composite_unique` and `0003_delivery_rate_per_litre` suggest piecemeal patching; a full schema-diff against the migration history was never done.

2. Public QR image endpoint as an unauthenticated PII/enumeration surface (customers/index.ts:86-108, GET /:id/qr.png). It is correctly outside the auth hook, but no finding examines: (a) the QR PNG is generated on every request (no storage/caching beyond a 24h Cache-Control header) — a cheap unauthenticated DoS via `generateQrPng` CPU; (b) whether the cuid `:id` truly resists enumeration; (c) it leaks existence (404 vs 200) of any customer id. Rate limit is 120/min/IP, easily abused.

3. Dashboard revenue semantics (dashboard/index.ts:97-115, 257). `revenue` sums ALL `status=PAID` payments in the window, which conflates one-time onboarding/renewal deposits with daily delivery billing, and includes manually-recorded cash. No finding checks whether the dashboard "revenue" number is even the metric the PRD §7 intends, or that it double-counts against the billing module's invoice totals. Trend-arrow deltas (pctChange) are also untested against real data.

4. Bulk-import commit is not atomic across rows AND silently allocates customer codes inside a per-row loop (customers/bulk.ts:179-257). Beyond ADM-04/SEC-03 (no re-validation), nobody examined: each row is its own transaction so a mid-batch failure leaves a partially-imported set with no rollback; `nextCustomerCode(prisma)` is called outside the row transaction (line 191) so a crash burns/duplicates codes; and the commit re-derives rate from the product but never re-checks phone uniqueness at commit time (only at validate), so a concurrent WhatsApp onboarding between validate and commit yields a P2002 surfaced only as a per-row failure string.

5. Bot-prompt interpolation safety and template/prompt drift (whatsapp/prompts.ts:219-224 + templates.ts). The audit looked at Meta template variable ordering (INT-05) but not the `getPrompt` ${var} interpolation: unknown vars are left as literal `${name}` and SENT to the customer (line 222), so any flow that forgets to pass a variable ships raw `${customerName}` to a paying customer. No finding audits which DEFAULT_PROMPTS keys are actually referenced by flows vs. orphaned, nor whether every flow `getPrompt` key has a matching default (a missing key throws → dead bot, the exact failure mode the file's own comment warns about).

6. Location-pin GET leaks customer PII with a long-lived, possibly-reusable token (location/index.ts:23-46). EDG-13 covers the POST race, but the GET is viewable repeatedly until `expiresAt` even after consumption (returns name + address + area + saved coordinates). No finding examines token entropy, the expiry duration set at issuance, or that a leaked/forwarded WhatsApp link exposes a customer's home address + GPS to anyone, unauthenticated and rate-limited only at 60/min.

7. CORS dev-mode origin reflection (server.ts:103-114). In non-production ANY localhost/127.0.0.1 origin is allowed with `credentials: true`. No finding checks the failure mode if NODE_ENV is unset/misconfigured in a deployed environment (defaults to 'development' per config.ts:19), which would turn the production API into a credentialed-CORS-open endpoint. The prod boot guard (config.ts:138-152) checks JWT/DB/ADMIN_ORIGIN but NOT that NODE_ENV is actually 'production'.

8. WhatsApp webhook media/unsupported-message handling (webhook.ts:118-167 + engine). Inbound image/document/audio/video are decoded into InboundMessage but no finding traces what the engine does with them mid-onboarding (e.g., customer sends a photo at ask_litres). Likely an unhandled kind that either crashes the handler (swallowed at line 103-106 → silent dead bot) or is misrouted. The status-callback TODO (line 109-112) is noted as ARC-10/EDG-06, but the inbound-media path is unexamined.

9. JWT lifecycle: no token revocation/rotation and a 7-day expiry with no logout invalidation (auth/index.ts:35 JWT_EXPIRES_IN '7d', no jti/denylist). `ensureActiveUser` mitigates deactivated users, but a leaked executive token stays valid for 7 days across all instances; password/PIN change does not invalidate existing tokens. No finding covers token revocation strategy or refresh-token absence — relevant given MOB-07 (plaintext localStorage token) makes leakage plausible.

10. Seed/demo-data contamination risk in production (apps/backend/prisma/seed.ts). The repo memory notes demo customers JHR-100801-803, a hardcoded COW_MILK rate of 64, and `SEED_RESET_BOT_PROMPTS`. No finding audits whether `db:seed` is gated against `NODE_ENV=production`, or whether the documented deploy flow (Procfile/release, per PRO-11) could run the seed against a prod DB and inject demo customers/executives into the live roster. The DEFAULT_RATE_PER_LITRE_INR constant vs Product-table rate (bulk.ts:187 fallback) is also a silent-divergence path.

11. Settings/holiday backend correctness and type coercion (settings/index.ts, services/settings.ts, modules/settings). WEB-02/03/04/13 cover the admin UI, but the backend `PUT /settings/:key` type-aware parsing, `settings.getNumber` fallback behavior (used in bulk.ts:171 and elsewhere), and the holiday composite-unique enforcement (date,scope) are not audited server-side. A bad JSON value persisted for a NUMBER/JSON setting could break scheduling or onboarding math at read time with no validation guard.

12. Deliveries cash-collection writing to Customer.balance during confirm (deliveries/index.ts imports PaymentMode/PaymentStatus; confirm path). DAT-02 covers balance-sign inversion and EDG-15/ADM-10 cover manual-payment dupes, but the confirm endpoint's optional cash-collection path (which can create a Payment AND mutate balance inside the delivery confirm transaction) was not separately examined for: idempotency on double-confirm (does re-confirm re-credit?), whether the cash Payment is linked to a delivery for reconciliation, and interaction with the EOD variance math (BAC-02/MIL-02). This is the single most money-sensitive write on the mobile side and sits at the intersection of several findings without being audited as its own unit.
